## 무엇을 하나

`code-review` 는 `HEAD` 와 당신이 지정한 고정점(커밋, 브랜치, 태그, `main`, `HEAD~5`) 사이의 차이를 두 축으로 검토합니다. **표준(Standards)** 축은 이 코드가 이 레포가 코드를 쓰는 방식을 따르는지 묻습니다. **스펙(Spec)** 축은 이 코드가 출발점이 된 이슈나 [스펙](https://www.aihero.dev/ai-coding-dictionary/spec)이 요구한 것을 하는지 묻습니다. 각 축은 자기만의 [서브에이전트](https://www.aihero.dev/ai-coding-dictionary/subagent)에서 돌아가므로 서로의 추론을 보지 못합니다.

두 축은 절대 합쳐지지 않고 순위가 다시 매겨지지도 않습니다. 보고서는 *축마다* 가장 심각한 문제 하나로 끝나고, 둘을 가로질러 단일 승자를 뽑기를 거부합니다. 어떤 변경은 한 축을 통과하면서 다른 축에서 떨어질 수 있기 때문입니다. 모든 관례를 지키면서 엉뚱한 것을 구현한 코드는 표준을 통과하고 스펙에서 떨어지며, [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)이 요구한 것을 정확히 하면서 레포의 관례를 깨뜨린 코드는 그 반대입니다. 섞인 판정은 통과한 축이 떨어진 축을 가리게 놔둡니다.

## 언제 꺼내 쓰나

`/code-review` 라고 치거나, 브랜치, PR, 진행 중인 작업, 또는 "X 이후로" 무언가를 검토해 달라고 하면 에이전트가 알아서 꺼내 씁니다.

| 당신의 상황 | 꺼낼 것 |
| --- | --- |
| 차이가 있고, 잘 만들어졌는지 *그리고* 맞는 것을 만들었는지 알고 싶음 | `code-review` |
| 차이에서 버그를 사냥하고 싶음: null 경로, 경쟁 상태, 하나 차이 오류 | 이것 말고 Claude Code 자체 내장 리뷰 (아래 이름 충돌 항목 참고) |
| 아직 아무것도 안 썼고 테스트 먼저 쓰고 싶음 | [tdd](https://aihero.dev/skills-tdd) |
| 스펙 전체를 리뷰까지 포함해 만들어야 함 | [implement](https://aihero.dev/skills-implement). 이 스킬을 스스로 부릅니다 |
| 차이 하나가 아니라 코드베이스 전체가 틀어졌음 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) |
| 뭔가 고장 났는데 이유를 모르겠음 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

고정점은 당신이 줘야 합니다. 주지 않으면 이 스킬은 추측하는 대신 요구합니다. 그다음 뭔가를 띄우기 전에 그 참조가 실제로 풀리는지와 차이가 비어 있지 않은지를 확인하므로, 오타 난 브랜치 이름은 서브에이전트 두 개 안쪽이 아니라 당신 눈앞에서 실패합니다.

## 사전 조건

표준 축은 아무것도 필요 없습니다. 레포가 문서화한 것(`CODING_STANDARDS.md`, `CONTRIBUTING.md` 같은 것)을 읽고, 레포가 아무것도 문서화하지 않았으면 내장 기준선으로 물러섭니다.

스펙 축은 스펙이 존재하고 찾을 수 있어야 합니다. 다음 순서로 찾습니다.

1. 커밋 메시지 안의 이슈 참조(`#123`, `Closes #45`, GitLab 의 `!67`). `docs/agents/issue-tracker.md` 를 통해 가져옵니다.
2. 당신이 인자로 넘긴 경로.
3. 브랜치나 기능 이름과 맞는 `docs/`, `specs/`, `.scratch/` 아래의 스펙 파일.
4. 당신에게 묻기.

1번은 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 가 쓰는 `docs/agents/issue-tracker.md` 에 의존합니다. 그게 없어도 경로를 직접 건네주면 이 축은 동작합니다. 스펙이 아예 없으면 스펙 서브에이전트는 건너뛰고, 보고서는 요구사항을 지어내는 대신 "스펙 없음" 이라고 적습니다.

## 두 개의 축

| | 표준 | 스펙 |
| --- | --- | --- |
| 묻는 것 | 잘 만들어졌는가? | 맞는 것인가? |
| 읽는 것 | 레포가 문서화한 표준, 그리고 코드 냄새 기준선 | 출발점이 된 이슈나 스펙 |
| 보고하는 것 | 문서화된 위반(확정일 수 있음), 그리고 냄새(항상 판단의 문제) | 빠졌거나 절반만 된 요구사항, 범위 부풀림, 잘못 구현된 요구사항 |
| 모든 지적이 인용하는 것 | 표준 파일과 규칙, 또는 이름 붙은 냄새와 해당 코드 덩어리 | 스펙의 해당 줄 |

당신의 표준을 모르는 범용 리뷰 스킬은 이 설계가 피하려는 바로 그것입니다. 그런 도구는 당신 코드베이스에서 의도된 것을 문제 삼고, 당신 코드베이스가 실제로 의존하는 불변 조건은 놓칩니다. 그래서 표준 축에서는 레포 자신의 문서가 [1차 출처](https://www.aihero.dev/ai-coding-dictionary/primary-source)이고, **레포가 항상 우선합니다**.

그 아래 바닥에 깔린 것이 **코드 냄새 기준선**으로, 파울러(Fowler)의 _Refactoring_ 3장에서 온 열두 개입니다. 수수께끼 같은 이름, 중복 코드, 기능 욕심, 데이터 뭉치, 기본형 집착, 반복되는 switch, 산탄총 수술, 발산하는 변경, 투기적 일반화, 메시지 사슬, 중개자, 거부된 유산. 각각은 라벨 붙은 어림짐작("기능 욕심 가능성")이지 확정 위반이 아니며, *무엇인가* → *어떻게 고치는가* 형태로 서술되어 불평이 아니라 다음 수가 붙은 채로 도착합니다. 당신의 린터가 이미 강제하는 것은 두 축 모두 건너뜁니다.

## 자주 나오는 질문

**Claude Code 자체 `/code-review` 와 충돌합니다. 어떻게 하죠?**

이 스킬에서 가장 많이 보고된 문제이고, 안 고쳐졌습니다. Claude Code 는 자체 `/code-review` 를 싣고 있는데 하는 일이 다릅니다. 그쪽은 차이에서 버그를 사냥하고, 이쪽은 스펙 준수와 레포 표준을 확인합니다. 이 라이브러리를 설치하면 둘 중 하나가 이기고, 어느 쪽이 이기는지는 설치 방식에 달렸습니다. 플러그인 마켓플레이스를 통하면 전부 `mattpocock-skills:` 접두사로 별칭이 붙어서 수식어 없는 이름으로는 내장 쪽에 닿기 어려워지고, 일반 skills 설치를 통하면 로컬 파일이 이겨서 이 스킬이 내장 쪽을 가립니다. 깔끔한 답 하나는 Claude Code 내장 스킬을 통째로 제거하는 것입니다. [컨텍스트](https://www.aihero.dev/ai-coding-dictionary/context)가 크게 절약되고 충돌은 문제가 아니게 됩니다. 가려지는 현상 자체는 Claude Code [하네스](https://www.aihero.dev/ai-coding-dictionary/harness)의 버그라고 볼 만하므로(스킬 저자는 이름을 마음대로 지을 수 있어야 합니다), 다른 답은 로컬 사본의 이름을 바꾸는 것입니다. 프론트매터를 고치거나 디렉터리 이름을 바꾸는 것은 `npx skills update` 가 되돌려 버립니다. 사용자들이 보고한 오래가는 우회책은 스킬을 새 이름으로 포크하고 관리 대상 묶음에서 `code-review` 를 빼는 것입니다. 어느 커밋에서 포크했는지 적어두면 나중에 손으로 다시 맞출 수 있습니다.

**서브에이전트들이 `/code-review` 를 또 불러서 에이전트를 더 띄웁니다.**

알려진 열린 버그이고, 여러 사람이 여러 하네스에서 재현했습니다. 표준과 스펙 프롬프트가 위임을 금지하지 않아서 서브에이전트가 이 스킬을 다시 발견하고 또 퍼뜨릴 수 있습니다. 어떤 보고는 에이전트 50개를 넘겼습니다. 사람들이 포크에 적용한 해결책은 두 서브에이전트 지시문 끝에 한 줄을 붙이는 것입니다. "`/code-review` 를 부르거나 추가 에이전트를 띄우지 말 것. 이 리뷰를 직접 수행할 것." 모든 스킬이 이 보호를 물려받도록 하네스 수준에서 처리하는 쪽을 선호하는 사람도 있습니다. 둘 다 아직 출시본에는 없습니다. 지켜보지 않고 돌린다면 에이전트 수를 확인하십시오.

**코드를 쓴 [세션](https://www.aihero.dev/ai-coding-dictionary/session)에서 바로 돌려도 되나요?**

새 세션을 권합니다. 어떤 독자의 표현대로입니다. "같은 컨텍스트가 자기를 리뷰하는 건 리뷰가 아니라 슬래시 명령어를 단 확증편향이다." 작성 세션 안의 리뷰 에이전트는 그 코드를 만들어낸 가정을 전부 들고 있는데, 독립적인 리뷰어라면 바로 그 컨텍스트가 없어야 합니다. 사람들이 [implement](https://aihero.dev/skills-implement) 에서 내장 리뷰 단계를 빼달라고 요청하는 이유도 이것입니다. 방금 차이를 쓴 그 세션 안에서 리뷰를 돌리니까요. 깨끗한 세션에서 `/code-review` 를 직접 부르는 쪽이 정직한 버전입니다.

**티켓마다 돌리나요, 끝에 한 번 돌리나요?**

둘 다 됩니다. 이 스킬이 대신 정해주지 않습니다. 티켓마다 돌리면 각 차이가 작게 유지되어 스펙 축이 대조할 스펙이 하나로 분명해집니다. `implement` 가 쓰는 방식입니다. 브랜치 끝에 몰아서 돌리면 티켓별 통과가 각각 놓치는 티켓 사이의 상호작용을 잡습니다. 헷갈리면 티켓마다 리뷰하고, 마지막에 브랜치 분기점을 기준으로 한 번 더 돌리십시오.

**지적을 믿어도 되나요?**

확인 없이는 안 됩니다. 서브에이전트 출력은 증거가 아니라 가설입니다. 어떤 팀은 줄글 기반 리뷰들이 그냥 통과시킨 호환성 깨짐 열두 건을 보고했습니다. 이 스킬은 두 보고서를 그대로 또는 가볍게 다듬어 모을 뿐 각 주장을 파일과 다시 대조하지 않으므로, 지적이 엉뚱한 위치를 인용하거나 영향을 부풀릴 수 있습니다. 행동하기 전에 각 지적의 인용을 읽으십시오. 모든 지적이 인용을 반드시 달아야 한다는 점(표준 규칙, 냄새와 그 코드 덩어리, 또는 스펙의 줄)이 애초에 이것을 확인 가능하게 만드는 장치입니다.

**돌릴 때마다 왜 매번 새로운 문제를 찾아내나요?**

고치면 새로운 표면이 생기기 때문이고, 표준 축의 판단에 속하는 절반이 실행마다 결정론적이지 않기 때문입니다. 어떤 독자가 이 루프를 그대로 묘사했습니다. "/code-review 와 /improve-code-architecture 는 매번 새로운 걸 찾아낸다. 고치고, 다시 돌리고, 또 그리고 또." 수렴한다는 보장은 없습니다. 한 번의 실행을 단서 목록으로 취급하고, 뒤에 인용된 규칙이 있는 것부터 처리한 뒤 멈추십시오. 깨끗하게 나올 때까지 루프로 돌리지 마십시오. 그런 날은 오지 않습니다.

**커밋 안 한 작업도 검토하나요?**

아닙니다. `<고정점>...HEAD` 형태의 점 세 개 차이를 보는데, 이건 공통 조상을 기준으로 재는 것이라 스테이징된 변경과 작업 트리 변경을 제외합니다. `implement` 가 중간 커밋을 만들지 않았다면 막 커밋하려던 작업은 리뷰에 보이지 않습니다. 먼저 커밋하고, 리뷰하고, 그다음 amend 하거나 fixup 을 얹으십시오.

## 제대로 동작하고 있다는 신호

- 잘못된 참조나 빈 차이에서는 서브에이전트를 띄우기 전에 시작을 거부합니다.
- 보고서가 하나로 합쳐진 목록이 아니라 `## Standards` 와 `## Spec` 아래 별개 블록 둘로 도착합니다.
- 모든 표준 지적이 당신 레포 파일 안의 규칙이나 열두 냄새 중 하나를 이름으로 대고 해당 코드 덩어리를 인용합니다. 모든 스펙 지적이 스펙의 한 줄을 인용합니다.
- 마무리 요약이 축마다 가장 심각한 문제를 주고 전체 승자 뽑기를 거부합니다.
- 스펙이 없을 때, 스펙 블록이 코드에서 유추한 요구사항을 나열하는 대신 없다고 말합니다.

## 전체에서 어디에 있나

`code-review` 는 빌드 사슬의 꼬리에 있는 리뷰 단계입니다. `grill-with-docs → to-spec → to-tickets → implement → code-review`. 당신이 가리키는 아무 브랜치나 PR 에 단독으로 쓰기도 합니다.

- [implement](https://aihero.dev/skills-implement) 가 가장 가까운 이웃입니다. 빌드를 굴리고, 커밋 전 마무리 리뷰로 이 스킬을 부릅니다.
- [to-spec](https://aihero.dev/skills-to-spec) 과 [to-tickets](https://aihero.dev/skills-to-tickets) 가 스펙 축이 대조할 문서를 만듭니다. 스펙이 흐릿하면 그 축도 흐릿해집니다.
- [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 가 코드베이스 전체를 보는 대응물입니다. 이 스킬은 언제나 차이 하나만 봅니다.

어떤 스킬이 상황에 맞는지 모르겠으면 [ask-matt](https://aihero.dev/skills-ask-matt) 가 전체 묶음을 가로질러 안내합니다.
