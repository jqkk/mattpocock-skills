## 무엇을 하나

`diagnosing-bugs` 는 까다로운 버그나 성능 퇴행에 대해 여섯 국면의 진단을 돌립니다. 재현 만들기, 최소화, 가설 순위 매기기, 계측, 회귀 테스트와 함께 고치기, 뒷정리.

**단단한(tight)** 피드백 루프가 생기기 전까지는 에이전트가 이론을 세우지 못하게 막습니다. 이름이 붙은 명령어 하나로, 이미 한 번 실행됐고, *이* 버그에서 빨강이 되고 고쳐지면 초록이 되는 것 말입니다. 버그 제보를 받은 코딩 에이전트의 기본 행동은 코드를 읽고 추측하는 것인데, 이 스킬은 그것을 막습니다. 빨강을 낼 수 있는 명령어가 없으면 2국면은 없습니다. 그 단 하나의 관문이 이 스킬의 존재 이유입니다. 그 뒤의 모든 것(이분 탐색, 가설 검증, 계측)은 신호만 있으면 기계적인 일입니다.

## 언제 꺼내 쓰나

`/diagnosing-bugs` 라고 치거나, 과제가 들어맞을 때 에이전트가 알아서 꺼내 씁니다. 모델이 부를 수 있는 스킬이고, "진단해" / "이거 디버그해" 또는 뭔가 고장 났다, 예외가 난다, 실패한다, 느리다는 보고에 반응합니다.

어려운 것들에 꺼내십시오. 한 번 봐서는 안 잡히는 버그, 간헐적으로 나는 불안정한 실패, 정상이던 두 지점 사이에 스며든 퇴행 같은 것입니다. 무거운 것이 설계 의도라서, 한 메시지로 답을 받고 싶은 질문에는 잘못된 도구입니다.

| 당신의 상황 | 어디로 갈 것인가 |
| --- | --- |
| 증상으로 서술할 수 있는 구체적인 결함 | 이 스킬 |
| 전후가 알려진 느린 엔드포인트나 응답 시간 퇴행 | 이 스킬. 성능 분기가 있습니다 (기준선을 재고 이분 탐색) |
| "이 코드베이스의 병목이 어디야?", 구체적 증상 없음 | 이 스킬이 아닙니다. 알려진 실패 하나를 진단할 뿐 감사를 하지는 않습니다 |
| 아직 확인도 정리도 안 된 남의 날것 버그 제보 | 먼저 [triage](https://aihero.dev/skills-triage) |
| 결함 추적이 아니라 설계 질문에 답하려는 일회용 코드 | [prototype](https://aihero.dev/skills-prototype) |
| 계획된 동작을 테스트 먼저 만들기 | [tdd](https://aihero.dev/skills-tdd) |
| 버그를 붙잡아 둘 좋은 이음매가 없음 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture). 이 스킬이 스스로 거기로 넘깁니다 |

## 단단한 루프가 곧 이 스킬이다

1국면에 유독 많은 노력이 들어가는데, 어려운 국면이 거기뿐이기 때문입니다. 이 스킬은 루프를 만드는 방법을 대략 선호 순서대로 사다리처럼 제시합니다.

1. 버그에 닿는 아무 이음매에서의 실패하는 테스트.
2. 돌아가는 개발 서버를 향한 curl 또는 HTTP 스크립트.
3. 고정 입력을 준 CLI 호출과, 정상으로 알려진 스냅샷과의 차이 비교.
4. DOM, 콘솔, 네트워크를 단언하는 헤드리스 브라우저 스크립트.
5. 재생된 기록: 저장해 둔 요청, 페이로드, 이벤트 로그를 코드 경로에 따로 흘려보내기.
6. 일회용 시험대: 시스템의 최소 부분집합, 함수 호출 하나.
7. 속성 기반 또는 퍼즈 루프. "가끔 출력이 틀림" 을 위한 것입니다.
8. `git bisect run` 에 건넬 수 있는 이분 탐색 시험대.
9. 차등 루프: 같은 입력, 구 버전 대 신 버전.
10. [사람이 개입하는](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) bash 스크립트, 최후의 수단. 이를 위해 스킬이 `scripts/hitl-loop.template.sh` 를 싣고 있습니다. 에이전트가 스크립트를 돌리고, 당신이 터미널의 프롬프트를 따라가면, 당신의 대답이 파싱 가능한 출력으로 돌아옵니다.

루프가 *있다*는 것이 목표가 아닙니다. **단단함**이 목표입니다. 빠르고(초 단위), 결정론적이고(매번 같은 판정), 날카롭고("죽지 않았다" 가 아니라 당신의 정확한 증상을 단언), 에이전트가 지켜보지 않아도 돌릴 수 있어야 합니다. 30초짜리 불안정한 루프는 없는 것보다 조금 나을 뿐입니다. 가끔만 나타나는 버그의 목표는 깨끗한 재현이 아니라 **재현율을 높이는 것**입니다. 트리거를 반복하고, 병렬로 돌리고, 부하를 주고, 잠깐씩 멈추는 구간을 끼워 넣어서 디버그할 수 있을 만큼 실패율을 올리십시오.

정말로 만들 수 없을 때는 멈추고 그렇다고 말하며, 시도한 것을 나열하고, [환경](https://www.aihero.dev/ai-coding-dictionary/environment) 접근 권한이나 수집된 산출물, 또는 임시 계측을 추가할 허락을 요청하도록 지시받았습니다. 그냥 가설부터 세우고 넘어가면 안 됩니다.

## 국면 사이의 관문

국면들은 체크리스트가 아니라 관문입니다. 각각은 특정 조건이 참이 되기 전까지 열리기를 거부합니다.

| 관문 | 참이어야 하는 것 |
| --- | --- |
| 2국면으로 | 이 버그에서 빨강이 될 수 있고, 이미 실행되어 출력까지 붙여진, 이름이 있는 명령어 |
| 3국면으로 | 재현이 실제로 재현되었고 *또한* 최소화되었을 것. 남은 요소가 전부 제 역할을 할 것 |
| 4국면으로 | 반증 가능한 가설 3~5개가 순위와 함께 존재하고, 각각이 자기 예측을 밝히며, 하나라도 검증되기 전에 당신에게 보여졌을 것 |
| 5국면으로 | 탐침이 특정 예측에 대응되고, 한 번에 변수 하나씩이며, 모든 디버그 로그에 `[DEBUG-a4f2]` 같은 태그가 붙어 뒷정리가 grep 한 번으로 끝날 것 |
| 완료 | 원래 재현이 더 이상 재현되지 않고, 계측이 사라졌고, 맞는 것으로 드러난 가설이 커밋 메시지에 적혔을 것 |

5국면에는 알아둘 만한 비상구가 있습니다. 회귀 테스트는 수정 전에 쓰이지만, 그것을 위한 **올바른 이음매**가 있을 때만 그렇습니다. 호출 지점에서 실제로 일어나는 모습 그대로 버그 패턴을 다루는 이음매 말입니다. 가능한 이음매가 너무 얕은 것뿐이라면, 스킬은 헛된 자신감을 주는 테스트를 쓰는 대신 그렇다고 말하도록 지시받았습니다. 그 부재 자체가 하나의 발견이고, 사후 분석을 `improve-codebase-architecture` 로 보내는 것도 그것입니다.

## 자주 나오는 질문

**그냥 직접 답을 듣고 싶은 가벼운 질문에도 발동합니다.**
이 스킬에서 가장 많이 보고된 문제이고, 실재합니다. 특히 GPT-5.6-Sol 에서 사용자들은 문제를 평범하게 설명하기만 해도 발동한다고 보고합니다. "모델이 꽤 격식 있는 diagnosing-bugs 스킬을 대신 발동시킨다. 그러고는 답이나 제안을 주기 전에 재현 시나리오를 구성한다(가치가 제한적인 모의 시나리오를 만드는 경우가 많다). 그 결과 답변이 상당히 늦어진다." [이슈 #578](https://github.com/mattpocock/skills/issues/578) 에 네 사람이 따로 같은 모양을 보고했습니다. 받아들여진 수정 방향은 가벼운 접근으로 시작해서 문제가 그럴 만할 때만 무거운 쪽으로 올라가는 것인데, 아직 반영되지 않았습니다. 이 스킬은 Claude Code 의 호출 동작에 맞춰 조정되어 있어서, 발동 문턱이 더 낮은 [모델](https://www.aihero.dev/ai-coding-dictionary/model)에서는 과하게 발동합니다. 단계화될 때까지의 실용적인 해결책은 원하는 바를 말하거나("진단하지 말고 그냥 답해줘") 당신의 [하네스](https://www.aihero.dev/ai-coding-dictionary/harness)에서 이 스킬의 모델 호출을 꺼두는 것입니다.

**코드베이스를 가리키며 성능 문제가 어디 있는지 물어봐도 되나요?**
아닙니다. 당신이 이미 이름 댈 수 있는 실패 하나를 진단합니다. 성능 분기는 증상이 있는 퇴행을 위한 것이고(기준선 측정을 세우고 이분 탐색, 먼저 재고 나중에 고치기), 선제적으로 훑는 용도가 아닙니다. 선제적 버전을 위한 스킬은 [제안됐다가 닫혔습니다](https://github.com/mattpocock/skills/issues/431). 현재 그것을 위한 스킬은 없습니다.

**수정을 쓰기 전에 멈추고 물어보나요?**
아닙니다. 사람이 개입하는 확인 지점은 3국면뿐입니다. 순위 매긴 가설 목록을 하나라도 검증하기 전에 보여주고, 당신이 자리에 없으면 자기 순위대로 진행합니다. 계측과 수정 사이에는 관문이 없어서, 당신이 근본 원인에 동의하기 전에 에이전트가 코드를 쓰기 시작할 수 있습니다. [이슈 #124](https://github.com/mattpocock/skills/issues/124) 가 그 관문을 요청하고 있고 아직 열려 있습니다. 원한다면 스킬을 부를 때 그렇게 말하십시오.

**이 버그 제보에 이미 `/triage` 를 돌렸습니다. 같은 일을 또 하는 건가요?**
부분적으로 그렇고, 어느 쪽 스킬도 그 사실을 인정하지 않습니다. 어떤 독자의 표현입니다. "triage 의 3단계는 사실상 diagnosing-bugs 1~2국면의 얕고 범위가 제한된 사례인데, 두 파일 중 어느 쪽도 상대를 언급하지 않는다." triage 는 "이게 실제로 버그인가, 표면은 어디까지인가" 를 범위를 제한해 한 번 훑고, 이 스킬은 철저한 버전을 합니다. triage 를 먼저 돌린 것이 낭비는 아니지만(그 확인 작업이 1국면의 재료 대부분을 주는 경우가 많습니다), 여기서 제대로 다시 하게 될 것이고, 그렇다고 알려주는 상호 참조는 없다고 예상하십시오.

**붙여넣는 재현 출력에 비밀 정보가 샐 수 있나요?**
그럴 수 있습니다. 이 스킬은 에이전트에게 호출과 그 출력을 붙여넣으라고 하고, HAR 파일, 로그 덤프, 코어 덤프 같은 산출물을 요청하라고 합니다. 그중 어느 것도 지시상 가려지지 않습니다. [이슈 #674](https://github.com/mattpocock/skills/issues/674) 가 정확히 이 점(자격 증명, 토큰, 쿠키, 개인 정보가 채팅이나 이슈나 PR 에 딸려 들어가는 것)을 제기하며 가림 가드레일을 제안합니다. 열려 있고 구현되지 않았습니다. 당분간 가리는 일은 당신 몫으로 두십시오. 특히 출력이 공개된 곳으로 나가기 전에 말입니다.

**보안 스캐너가 이 스킬을 고위험으로 표시했습니다.**
Snyk 가 표시하는데, 오탐입니다. 이 묶음에서 실행 가능한 셸 스크립트(`hitl-loop.template.sh`)를 싣고, 그것을 실행하라는 지시와 개발 서버에 curl 하라는 지시를 함께 담은 유일한 스킬입니다. `.sh` 파일 포함에 실행 지시에 외부로 나가는 HTTP 까지 더해지면 정적 스캐너가 걸기에 충분합니다. 스크립트 자체는 사람의 입력을 기다리는 `read -r -p` 프롬프트 30줄 정도입니다. 스캐너는 입증된 공격이 아니라 기능 표면을 등급 매기고 있는 것입니다.

**`/diagnose` 는 어떻게 됐나요?**
v1.0.0 에서 `/diagnosing-bugs` 로 이름이 바뀌었습니다. 옛 이름은 더 이상 없습니다. `/diagnose` 를 엮어 쓰는 당신의 무언가(감싸는 스킬, 저장해 둔 프롬프트)가 있다면 갱신이 필요합니다.

## 제대로 동작하고 있다는 신호

- 이론을 하나라도 내놓기 전에 명령어와 그 빨강 출력을 보여줍니다. 이론이 먼저 오면 이 스킬은 돌고 있지 않은 것입니다.
- 재현해 낸 실패가 오는 길에 발견한 비슷한 것이 아니라 당신이 보고한 그 실패입니다.
- 추측을 시작하기 전에 재현을 줄이고, 남은 조각 하나하나가 왜 필요한지 말할 수 있습니다.
- 하나라도 검증되기 전에, 각각 반증 가능한 예측이 달린 가설 3~5개의 순위 목록을 보게 됩니다.
- 추가한 모든 디버그 로그에 `[DEBUG-a4f2]` 같은 태그가 붙어 있고, 끝났다고 선언할 때 그 태그로 grep 하면 아무것도 안 나옵니다.
- 커밋이나 PR 메시지가 어느 가설이 맞았는지 이름을 댑니다.
- 테스트로 버그를 붙잡아 둘 수 없을 때, 얕은 테스트를 쓰는 대신 그렇다고 분명히 말합니다.

## 전체에서 어디에 있나

`diagnosing-bugs` 는 아무 때나 꺼내 쓰는 독립 스킬입니다. 뭔가 고장 났을 때 들어가고, 수정과 회귀 테스트가 들어오면 빠져나옵니다. 상태를 들고 있지 않고 사전 설정도 필요 없습니다. [ask-matt](https://aihero.dev/skills-ask-matt) 은 "뭔가 고장 났음" 을 여기로 보냅니다.

이웃 둘이 중요합니다. 진짜 발견이 "이 코드에는 버그를 붙잡아 둘 이음매가 없다" 인 경우 [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 가 [인계](https://www.aihero.dev/ai-coding-dictionary/handoff)를 받습니다. 그 추천은 수정이 들어간 뒤, 정보가 더 쌓였을 때 이루어집니다. [triage](https://aihero.dev/skills-triage) 는 남이 날것으로 보낸 버그에 대해 이 스킬의 상류에 있고, 같은 앞 두 국면의 얕은 버전을 수행합니다.
