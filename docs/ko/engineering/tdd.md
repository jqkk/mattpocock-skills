## 무엇을 하나

`tdd` 는 기능을 만들거나 버그를 고칠 때 테스트를 먼저 씁니다. 실패하는 테스트 하나, 그 테스트를 통과시킬 만큼만의 코드, 그다음 동작. 이 루프가 남길 가치가 있는 테스트를 만들어내도록 기준을 함께 들고 있습니다. 좋은 테스트란 무엇인지, 테스트가 어디에 놓이는지, 목(mock, 가짜 대역)은 무엇을 위한 것인지, 그리고 테스트 묶음을 조용히 망가뜨리는 세 가지 안티패턴이 그 기준입니다.

이 스킬은 당신이 먼저 합의하지 않은 이음매(seam)에는 테스트를 쓰지 않습니다. 테스트가 하나라도 생기기 전에, 어떤 공개 경계에서 테스트할 작정인지 이름을 대고 당신의 확인을 기다립니다. 테스트에 쓸 수 있는 노력은 유한하고, 그 노력을 모든 예외 상황이 아니라 핵심 경로에 쓰는 지점이 바로 여기이기 때문입니다. 또 하나 알아둘 것은 `tdd` 가 **참조 문서**이지 진행자가 아니라는 점입니다. 루프의 규칙을 들고 있을 뿐이고, 그 규칙을 적용하는 [세션](https://www.aihero.dev/ai-coding-dictionary/session)은 다른 쪽(당신, 또는 [implement](https://aihero.dev/skills-implement))이 굴립니다.

## 언제 꺼내 쓰나

`/tdd` 라고 치거나, 과제가 들어맞을 때 [에이전트](https://www.aihero.dev/ai-coding-dictionary/agent)가 알아서 꺼내 씁니다. 기능을 만들거나 버그를 테스트 먼저 방식으로 고칠 때, 또는 당신이 "red-green-refactor" 라고 말할 때입니다.

입력과 눈에 보이는 출력이 있는 구체적인 동작이 있고, 리팩터링을 견디는 테스트를 원할 때 꺼내십시오.

| 당신의 상황 | 어디로 갈 것인가 |
| --- | --- |
| 입력과 출력이 정해진 동작 (비즈니스 로직, 요청/응답 계약, 변환, 검증) | `tdd` |
| 동작이 아직 확정되지 않음 | [to-spec](https://aihero.dev/skills-to-spec). 코드가 써지기 전에 테스트 이음매까지 합의해 줍니다 |
| 진짜 질문이 테스트가 아니라 인터페이스의 모양임 | [codebase-design](https://aihero.dev/skills-codebase-design) |
| [스펙](https://www.aihero.dev/ai-coding-dictionary/spec)이나 [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)이 있고 빌드 전체를 맡기고 싶음 | [implement](https://aihero.dev/skills-implement). 티켓마다 `tdd` 를 굴립니다 |
| 설정, 배선, 접착 코드, 타입 주석, 단순 CRUD 위임 | 여기에 맞는 것이 없습니다. 아래의 열린 구멍을 보십시오 |

마지막 행은 취향 문제가 아니라 진짜 구멍입니다. 이 스킬은 이음매를 *어디에* 둘지 정하지만, 어떤 변경이 애초에 이 루프를 굴릴 값어치가 있는지를 판단하는 장치는 아무것도 없습니다. 대조할 독립적인 근거가 없는 변경에 이 루프를 돌리면 구현을 그대로 옮겨 적은 테스트가 나옵니다. 스킬 자신이 경고하는 동어반복 안티패턴에, 반대편에서 도달하는 셈입니다. [이슈 #746](https://github.com/mattpocock/skills/issues/746) 이고 아직 열려 있습니다. 닫히기 전까지 그 판단은 당신이나 당신의 `CLAUDE.md` 몫입니다.

## 사전 조건

[codebase-design](https://aihero.dev/skills-codebase-design) 이 설치되어 있어야 합니다. `tdd` 는 예전에 깊은 모듈(deep module)과 인터페이스 설계 노트를 직접 들고 있었지만, v1.0 에서 공용 스킬에 넘기고 지웠습니다. 지금은 인터페이스 설계 어휘를 그쪽에 기대고 있습니다. 그 외에는 없습니다. 이 스킬은 [무상태](https://www.aihero.dev/ai-coding-dictionary/stateless)라서 자기 파일을 쓰지 않습니다.

## 루프, 그리고 루프가 돌아가는 이음매

세 개의 낱말이 이 스킬을 지탱합니다.

**빨강 → 초록 (red-green).** 실패하는 테스트를 먼저 쓰고, 그것을 통과시킬 만큼만 코드를 씁니다. 그다음 테스트를 미리 내다보지 않습니다. 리팩터 단계는 없습니다. 2026년 6월에 빠졌는데, 에이전트가 사실상 한 번도 수행하지 않았고, 리뷰와 구현은 별개 세션으로 나눌 때 더 잘 동작하기 때문입니다. 리팩터링은 [code-review](https://aihero.dev/skills-code-review) 의 몫입니다.

**수직 조각 (vertical slice).** 이음매 하나, 테스트 하나, 최소 구현 하나, 그리고 반복. 첫 번째 주기는 하나의 경로를 처음부터 끝까지 증명하는 **예광탄(tracer bullet)** 입니다. 반대는 수평 조각내기입니다. 테스트를 전부 먼저 쓰고 코드를 전부 나중에 쓰는 방식이죠. 뭉치로 쓴 테스트는 *상상한* 동작을 검증하고, 사용자가 실제로 하는 일이 아니라 사물의 모양을 확인하며, 구현을 이해하기도 전에 테스트 구조에 발을 묶습니다.

**미리 합의된 이음매 (pre-agreed seam).** 이음매란 안쪽에 손을 넣지 않고 동작을 관찰하는 공개 경계입니다. 규칙은 절대적입니다. 확인되지 않은 이음매에는 테스트를 쓰지 않습니다. 전체 사슬에서는 이음매를 더 앞단인 [to-spec](https://aihero.dev/skills-to-spec) 에서 합의합니다. "`/tdd` 는 미리 합의된 테스트 이음매에서만 작업하도록 지시받고, `/code-review` 는 합의된 이음매만 쓰였는지 확인한다." 단독으로 불렸을 때는 `tdd` 가 당신에게 직접 묻습니다.

막으려고 쓰인 세 가지 안티패턴입니다.

| 안티패턴 | 알아보는 신호 |
| --- | --- |
| 구현에 얽매인 테스트 | 동작은 그대로인데 내부 함수 이름만 바꿔도 테스트가 깨집니다. 내부 협력자를 목으로 대체했거나, 호출 횟수를 단언했거나, 인터페이스 대신 데이터베이스 쿼리로 검증했을 때입니다. |
| 동어반복 | 기대값을 코드가 계산하는 방식 그대로 계산해서, 구조상 무조건 통과합니다. 기대값은 다른 데서 와야 합니다. 검증된 리터럴, 손으로 풀어본 예제, 스펙 같은 것입니다. |
| 수평 조각내기 | 구현이 하나도 없는 상태에서 테스트 뭉치가 먼저 들어왔습니다. |

목은 시스템 경계에만 씁니다. 외부 API, 시간, 난수, 경우에 따라 파일시스템이나 데이터베이스입니다. 당신이 만든 모듈에는 쓰지 않습니다.

## 자주 나오는 질문

**왜 리팩터를 안 하나요? 설명에는 "red-green-refactor" 라고 쓰여 있는데요.**

리팩터 단계는 제거됐는데 설명은 안 고쳤기 때문입니다. 제거는 의도한 것이었습니다. 에이전트가 사실상 하지 않았고, 구현과 리뷰를 별개 세션으로 유지하는 쪽이 더 잘 돌아갑니다. 결과물이 교과서적 정의의 TDD 로 쳐주느냐보다, 그 루프가 더 나은 코드를 만드느냐가 중요합니다. 트리거 문구와 본문이 어긋나는 문제는 [이슈 #589](https://github.com/mattpocock/skills/issues/589) 로 올라가 있고 아직 열려 있어서, "red-green-refactor" 는 여전히 이 스킬을 부르는 문구로 동작합니다. 실제로 얻는 것은 빨강 → 초록이고, 리팩터링은 [code-review](https://aihero.dev/skills-code-review) 에서 일어납니다.

**테스트 이음매를 고르라고 하는데 뭘 골라야 할지 모르겠습니다.**

이 스킬에서 가장 많이 보고된 마찰입니다 ([이슈 #607](https://github.com/mattpocock/skills/issues/607)). 프롬프트가 후보 이음매를 이름만 나열하고, 각각이 무엇을 잡고 무엇을 놓치는지는 말해주지 않아서 라벨만 보고 고르는 셈이 됩니다. 아직 고쳐진 게 없습니다. 실용적인 우회책은 답하기 전에 에이전트에게 트레이드오프를 물어보는 것입니다. 컴포넌트 수준 이음매가 놓치는 것을 통합 이음매는 무엇을 잡는지, 그리고 얼마나 느려지는지. 사슬이 이음매를 `to-spec` 에서 미리 합의하는 이유도 이것입니다. 거기서는 프롬프트 하나가 아니라 기능 전체가 시야에 들어와 있습니다.

**빨강이 먼저라고 써 있는데도 테스트보다 구현을 먼저 썼습니다.**

일어납니다. 어떤 사용자가 [모델](https://www.aihero.dev/ai-coding-dictionary/model)을 밀어붙여 유난히 솔직한 답을 받아냈습니다. "스킬에 '한 번에 테스트 하나, 올바른 이유로 실패하는지 확인하라'고 쓰여 있는 걸 알고 있었다. 읽었다. 그냥 평소 습관으로 빠졌다." 이 스킬은 그 사실을 안고 가도록 쓰여 있습니다. 어떤 지시도 에이전트를 100% 따르게 만들지 못하고, 이 점을 더 세게 강제하면 얻는 것에 비해 에이전트의 재량을 지나치게 묶습니다. 엄격히 지켜지지 않아도 이 루프는 굴릴 값어치가 있습니다. 결과가 전반적으로 더 낫기 때문입니다. 특정 조각에서 엄격한 준수가 중요하다면, 스킬이 강제해 주리라 믿지 말고 진행을 지켜보십시오.

**브라우저 테스트나 종단간(end-to-end) 테스트를 먼저 써야 하나요?**

보통은 아니고, 이 스킬이 그걸 막아주지도 않습니다. 어떤 사용자가 에이전트가 Playwright 테스트를 먼저 쓴 뒤, 아직 존재하지도 않는 기능을 두고 긴 루프를 태워가며 재실행하다가 결국 *테스트*가 잘못됐다고 결론 내린 사례를 보고했습니다. 이건 당신의 `CLAUDE.md` 에서 설정하십시오. 브라우저 테스트는 빨강 → 초록 피드백 루프가 값을 못 할 만큼 느립니다. 동작이 돌아간 뒤에 쓴다고 레포의 `CLAUDE.md` 에 선언해 두십시오.

**`/tdd` 가 `/implement` 나 강의의 `/do-work` 를 대체하나요?**

아닙니다. `/tdd` 는 방법론을 문서화한 것이고, `/implement` 는 아주 단순한 작업 → 피드백 → 커밋 루프로서 `/do-work` 의 직접적인 대체재입니다. 강의의 단일 `/do-work` 단계는 이제 `/implement`, `/tdd`, `/code-review` 로 나뉘었습니다. 티켓 하나를 두고 뭘 돌릴지 묻는 거라면 답은 거의 항상 `/implement` 입니다.

**깊은 모듈과 인터페이스 설계 내용은 어디로 갔나요?**

v1.0 에서 [codebase-design](https://aihero.dev/skills-codebase-design) 으로 갔습니다. 여러 스킬이 하나의 어휘를 공유하도록 일반화됐습니다. `refactoring.md` 도 같이 빠졌습니다. 리팩터링은 이제 [code-review](https://aihero.dev/skills-code-review) 의 일이고, 그 스킬이 파울러(Fowler)의 코드 냄새 목록을 기준선으로 들고 있습니다.

**내 다른 티켓들을 알고 있나요?**

아닙니다. 티켓 하나를 두고 돌리면 형제 티켓에 속한 작업을 태연히 제안합니다. 나머지 이슈 그래프를 볼 수 없기 때문입니다 ([이슈 #129](https://github.com/mattpocock/skills/issues/129)). 이건 `tdd` 의 일이 아니라는 것이 유지보수 쪽 입장입니다. 티켓과 함께 스펙을 넘겨주면 도움이 되고, 애초에 티켓 크기를 알맞게 자르는 쪽이 더 도움이 됩니다.

## 제대로 동작하고 있다는 신호

- 테스트 파일이 하나라도 생기기 전에, 어느 이음매에서 테스트할지 이름을 대고 멈춰서 기다립니다.
- 테스트 하나가 나타나 빨강이 되고, 통과할 만큼만 코드가 붙고, 그다음에야 다음 테스트가 나타납니다. 테스트 뭉치 뒤에 코드 뭉치가 오지 않습니다.
- 테스트 이름이 내부 구조("checkout calls paymentService.process")가 아니라 능력("user can checkout with valid cart")으로 읽힙니다.
- 단언문의 기대값이 스펙까지 거슬러 갈 수 있는 리터럴이지, 코드가 계산하는 방식을 다시 계산한 값이 아닙니다.
- 내부 함수 이름을 바꿔도 테스트 묶음에서 깨지는 것이 없습니다.
- 목이 외부 경계(결제 API, 시계)에만 나타나고 당신의 모듈 주위에는 절대 나타나지 않습니다.

## 전체에서 어디에 있나

`tdd` 는 독립된 단계가 아니라 주 사슬의 빌드 단계 안에 들어 있는 엔진입니다.

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

[to-spec](https://aihero.dev/skills-to-spec) 이 테스트 이음매를 앞단에서 합의하고, [implement](https://aihero.dev/skills-implement) 가 티켓마다 `tdd` 를 굴리고, [code-review](https://aihero.dev/skills-code-review) 가 나중에 합의된 이음매만 쓰였는지 확인하며 `tdd` 가 더 이상 하지 않는 리팩터링을 맡습니다. 다른 이웃은 [codebase-design](https://aihero.dev/skills-codebase-design) 으로, `tdd` 가 쓰는 이음매와 깊은 모듈 어휘의 공용 출처입니다. 전체 스펙이 없더라도 구체적인 동작을 만들 일이 있으면 단독으로 꺼내 써도 됩니다. 어떤 스킬이 내 상황에 맞는지 모르겠으면 [ask-matt](https://aihero.dev/skills-ask-matt) 가 안내해 줍니다.
