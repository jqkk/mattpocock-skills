## 무엇을 하나

`to-tickets` 는 계획이나 [스펙](https://www.aihero.dev/ai-coding-dictionary/spec), 또는 지금 진행 중인 대화를 받아서 이슈 트래커 위의 **[티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)** 묶음으로 쪼갭니다. 각 티켓은 자기 **차단 관계**를 선언합니다. 시작하기 전에 끝나야 하는 다른 티켓들 말입니다.

모든 티켓은 **예광탄**입니다. 변경의 모든 계층(스키마, API, UI, 테스트)을 관통하는 좁지만 완결된 경로이고, 들어가는 순간 그것만으로 시연할 수 있습니다. 이 제약이 일을 나누는 뻔한 방식과 다르게 동작하게 만듭니다. 뻔한 방식은 한 번에 한 계층씩 자르고 끝에 통합하는 것이죠. 또한 각 티켓을 새 [컨텍스트 윈도](https://www.aihero.dev/ai-coding-dictionary/context-window) 하나에 들어가는 크기로 잡습니다. 그 티켓을 집어 들 대상이 당신 스펙을 한 번도 본 적 없는 [세션](https://www.aihero.dev/ai-coding-dictionary/session)이기 때문입니다.

## 언제 꺼내 쓰나

`/to-tickets` 라고 직접 쳐서 부릅니다. [에이전트](https://www.aihero.dev/ai-coding-dictionary/agent)가 알아서 꺼내 쓰지 않습니다.

| 당신이 있는 곳 | 무엇을 돌릴 것인가 |
| --- | --- |
| 스펙 이슈가 있고 빌드가 여러 세션에 걸침 | `/to-tickets`, 또는 `/to-tickets #<스펙_이슈>` |
| 계획이 대화 안에만 있고 정리된 적 없음 | `/to-tickets` 가 스레드를 직접 읽습니다. 스펙 불필요 |
| 변경 전체가 컨텍스트 윈도 하나에 들어감 | [implement](https://aihero.dev/skills-implement). 티켓은 건너뛰십시오 |
| 아직 아무것도 결정 안 됨 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs), 그다음 [to-spec](https://aihero.dev/skills-to-spec) |
| [wayfinder](https://aihero.dev/skills-wayfinder) 지도가 정리됨 | 먼저 [to-spec](https://aihero.dev/skills-to-spec) 으로 지도를 접고, 그다음 `/to-tickets` |

`to-tickets` 가 만든 티켓은 구조상 이미 에이전트가 작업할 준비가 된 것들입니다. 그 위에 [triage](https://aihero.dev/skills-triage) 를 돌리지 마십시오. triage 는 남에게서 들어온 일을 위한 것입니다.

## 사전 조건

`to-tickets` 는 트래커에 발행하므로, [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 가 이 레포에 트래커와 분류 라벨 어휘를 설정해 뒀어야 합니다. 어느 종류든 됩니다. GitHub 나 Linear 같은 진짜 트래커도 되고, 기본으로 지원되는 `.scratch/` 아래 로컬 마크다운 파일도 됩니다.

## 계층이 아니라 예광탄

**수평** 조각은 변경의 한 계층을 내놓습니다. 모든 계층이 들어오기 전까지는 아무것도 동작하지 않고, 각 티켓의 인수 조건이 다른 티켓이 소유한 작업에까지 손을 뻗어야 합니다. **수직** 조각(예광탄)은 모든 계층을 한꺼번에 관통하는 얇은 경로 하나를 내놓으므로, 혼자서 검증 가능하고 자기가 채점하는 모든 것을 자기가 소유합니다.

이것이 사람들이 가장 자주 깨는 규칙이고, 결과도 잘 기록돼 있습니다. 어떤 팀이 계층별로 자른 26개 티켓 더미(말뭉치, 생성기, 집계기, 선택기)를 돌렸다가 닫힌 티켓 하나당 대략 스무 번의 에이전트 실행을 겪었고, 그중 약 4분의 3이 재작업이었습니다. 그들의 사후 분석은 모든 실패 유형을 구현이 아니라 수평 조각내기까지 되짚었습니다.

무언가 발행되기 전에 두 가지가 일어납니다. `to-tickets` 는 선행 리팩터링("변경을 쉽게 만들고, 그다음 쉬워진 변경을 하라" 는 원칙)을 찾아 그 작업을 앞에 놓습니다. 그다음 쪼갠 결과를 번호 매긴 목록으로 제시하고 당신에게 캐묻습니다. 알갱이 크기가 맞는가, 차단 관계가 진짜인가, 합치거나 쪼갤 것이 있는가. 당신이 승인하기 전까지는 아무것도 트래커에 닿지 않고, 그 캐묻기가 반박할 자리입니다.

## 차단 관계

이 관계가 산출물의 핵심입니다. 트래커에 따라 두 가지로 읽힙니다.

| 트래커 | 관계가 사는 곳 | 어떻게 처리하나 |
| --- | --- | --- |
| 로컬 마크다운 | `.scratch/<기능>/issues/<NN>-<슬러그>.md` 로 티켓마다 한 파일, 막는 것 먼저 번호가 매겨진 텍스트 | 위에서 아래로, 손으로 |
| 진짜 트래커 (GitHub, Linear) | 트래커 고유의 차단 링크, 또는 지원하는 경우 하위 이슈 | 막는 것이 전부 끝난 티켓은 **작업 전선**에 있고 집어 들 수 있습니다 |

어느 쪽이든 관계는 티켓 안에 삽니다. 매체가 정하는 것은 그것에 대해 병렬로 뭔가를 할 수 있느냐뿐입니다. `to-tickets` 는 산출물을 만들고, 그것을 돌리는 일(한 번에 한 세션이든 여러 대이든)은 스킬이 아니라 당신 몫입니다.

## 넓은 리팩터링 예외

한 가지 모양이 예광탄 규칙을 깹니다. **넓은 리팩터링**은 기계적인 변경 하나(컬럼 이름 바꾸기, 공유 심볼의 타입 바꾸기)인데 **파급 범위**가 코드베이스 전체로 퍼져서, 편집 한 번이 호출 지점 수천 개를 깨뜨리고 어떤 수직 조각도 초록으로 들어갈 수 없는 경우입니다.

`to-tickets` 는 그것을 대신 **확장-축소(expand-contract)** 로 배치합니다.

- **확장**: 옛 형태 옆에 새 형태를 추가합니다. 아무것도 깨지지 않습니다.
- **이전**: 호출 지점을 파급 범위 크기로 묶어(패키지별, 디렉터리별) 옮깁니다. 묶음마다 티켓 하나이고, 각각 확장에 막혀 있습니다. 옛 형태가 아직 있으므로 CI 는 초록으로 유지됩니다.
- **축소**: 남은 호출자가 없어지면 옛 형태를 지웁니다. 모든 이전 묶음에 막힌 티켓 하나로요.

묶음마저 혼자서는 초록을 유지할 수 없는 경우, 그것들이 통합 브랜치를 공유하고 전부가 마지막 통합-검증 티켓 하나를 막습니다. 초록은 거기서만 약속됩니다.

## 자주 나오는 질문

**세 줄짜리 변경에 티켓 열두 개를 만들었습니다.**
과도한 쪼개기가 이 스킬에서 가장 많이 보고된 마찰이고, 실무자들 사이에서 일관됩니다. [모델](https://www.aihero.dev/ai-coding-dictionary/model)이 기본적으로 원자 단위로 가고, 그것들을 의미 있게 만들어줄 묶음 짓기를 잃어버립니다. 캐묻기 단계가 정확히 이것을 위해 있습니다. 합치라고 하면 합칩니다. 더 깊은 답은 티켓에 바닥이 있다는 것입니다. 변경 전체가 컨텍스트 윈도 하나에 들어간다면 이 스킬 자체가 필요 없습니다. 바로 [implement](https://aihero.dev/skills-implement) 로 가십시오.

**티켓이 계층마다 하나씩 나왔습니다. 스키마 전부가 하나, API 전부가 다른 하나.**
수직 조각 규칙이 겨냥해 쓰인 실패이고, 스킬은 여전히 가끔 이걸 만들어냅니다. 캐묻기 단계에서 티켓마다 질문 하나로 잡으십시오. 이게 끝나면 내가 무엇을 시연할 수 있나? 답이 없는 티켓은 수평 조각입니다. 그래서 티켓마다 "시연 경로" 줄을 추가하는 사람들이 있고, 그것이 모델을 수직 분해 쪽으로 민다고 보고합니다.

**GitHub 에서 티켓이 스펙 이슈의 하위 이슈로 만들어지지 않았습니다.**
알려졌고 안 고쳐졌습니다. 열 번이 넘는 실행과 여러 모델에서 보고됐고 [이슈 #554 에 가장 자세히](https://github.com/mattpocock/skills/issues/554) 있으며, Claude 보다 Codex 에서 더 심합니다. `gh` 는 v2.94 부터 이것을 기본 지원합니다. `gh issue create --parent <n>`, 그리고 사후에는 `gh issue edit <부모> --add-sub-issue <n>`. 트래커 템플릿이 그것을 선호하게 되기 전까지는, 실행 뒤에 부모 링크를 직접 연결하는 것이 확실한 방법입니다.

**"Blocked by" 가 진짜 차단 링크 대신 이슈 본문에 적혔습니다.**
같은 부류의 문제이고 [이슈 #513 에 보고](https://github.com/mattpocock/skills/issues/513)돼 있습니다. 거기서 에이전트는 GitHub 에 기본 차단 관계가 아예 없다고 단언하기까지 했습니다. 있습니다. `gh issue create --blocked-by 12,15`. 막는 쪽이 먼저 발행되므로 생성 시점에 그 번호가 항상 있습니다. 본문 텍스트는 기본 관계가 없는 트래커를 위한 대비책이지 기본값이 아닙니다.

**로컬 티켓은 어디로 가나요? v1.1 노트에는 루트의 `tickets.md` 라고 했는데요.**
그렇게 적혀 있었고, 그건 버그였습니다. 공유 파일 하나는 병렬 에이전트가 쓸 때 충돌하기도 했습니다. 이제 로컬 모드는 `.scratch/<기능-슬러그>/issues/<NN>-<슬러그>.md` 로 티켓마다 한 파일을 의존 순서대로 씁니다. 로컬 트래커 템플릿이 이미 서술하던 배치와 맞는 형태입니다. `NN` 접두사는 진짜 티켓 번호라서, 긴 제목을 다시 치는 대신 `/implement 03` 이 동작합니다.

**스펙을 읽으려 할 때 계속 잘렸습니다.**
아주 큰 스펙은 트래커 이슈가 깔끔하게 되돌려주는 한계를 넘어설 수 있고, 대신 볼 로컬 사본도 없습니다. 그러면 에이전트가 조각을 다시 가져오느라 [도구 호출](https://www.aihero.dev/ai-coding-dictionary/tool-call)을 태우고 끝에 도달하지 못합니다. `/to-spec` 과 `/to-tickets` 사이에 [비우거나](https://www.aihero.dev/ai-coding-dictionary/clearing) [압축하지](https://www.aihero.dev/ai-coding-dictionary/compaction) 마십시오. 같은 컨텍스트 윈도에서 돌리면 스펙을 다시 가져올 일이 아예 없습니다.

**인수 조건이 아무것도 채점하지 않았습니다. 작업 전에 이미 통과한 것도 있었습니다.**
템플릿이 조건을 요구하면서 그것이 실패할 수 있어야 하는지는 말하지 않아서 이런 일이 생깁니다. 반복되는 모양이 셋입니다. 기준 커밋에서 이미 참인 조건, 다른 티켓이 소유한 작업으로만 만족될 수 있는 조건, 그리고 산출물에서 도출되지 않고 요청을 그대로 되뇌는 조건입니다. 수직 조각내기가 대부분을 막지만(이전에 없던 동작을 내놓는 조각은 구조상 기준 커밋에서 빨강입니다), 손으로 확인할 가치가 있습니다. 조건마다 그것이 거짓임을 보여줄 관찰을 이름으로 대고, 구현자가 출발하는 커밋에서 그것이 실패하는지 확인하십시오.

**티켓이 발행됐습니다. 실제로 어떻게 돌리나요?**
이 스킬은 산출물에서 멈추고, 자동 배분 모드는 없습니다. 배분은 수동입니다. 보드를 보고, 열린 차단이 없는 티켓 수를 세고, 그만큼 에이전트 세션을 여십시오. 새 컨텍스트 하나에 티켓 하나, 사이사이 비우기. [implement](https://aihero.dev/skills-implement) 가 끝날 때 GitHub 에서든 로컬 마크다운에서든 티켓을 확실히 닫거나 체크해 주지 않는다는 점을 유념하십시오. 티켓 상태를 갱신하는 것은 당신 몫입니다.

## 제대로 동작하고 있다는 신호

- 모든 티켓이 "이게 끝나면 내가 무엇을 시연할 수 있나?" 에 답을 갖고 있고, 그 답이 계층이 아니라 동작입니다.
- 무언가 발행되기 전에 목록이 번호와 각 항목의 "Blocked by" 줄과 함께 당신에게 돌아옵니다.
- 맨 위의 티켓은 막는 것이 없고 바로 시작할 수 있습니다.
- 티켓 본문에 파일 경로나 줄 번호가 없습니다. 프로토타입이 만들어낸 조각은 예외입니다.
- 각 티켓이 당신 없이도 새 세션이 끝낼 수 있는 물건으로 읽힙니다.
- 찾아낸 선행 리팩터링이 있다면 기능 티켓에 섞이지 않고 순서 맨 앞에 있습니다.

## 전체에서 어디에 있나

`to-tickets` 는 주 빌드 사슬의 한 단계입니다.

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review
```

상류는 자를 대상인 확정된 스펙을 건네주는 [to-spec](https://aihero.dev/skills-to-spec) 입니다. 둘을 끊기지 않은 컨텍스트 윈도 하나에 두십시오. 하류는 [implement](https://aihero.dev/skills-implement) 로, 새 세션마다 티켓 하나를 만들고, 테스트를 위해 [tdd](https://aihero.dev/skills-tdd) 를 굴리며, [code-review](https://aihero.dev/skills-code-review) 로 마무리합니다. 어떤 스킬이나 흐름이 맞는지 모르겠으면 [ask-matt](https://aihero.dev/skills-ask-matt) 이 안내합니다.
