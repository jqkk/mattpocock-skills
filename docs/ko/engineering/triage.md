## 무엇을 하나

`triage` 는 프로젝트 트래커의 이슈들을 하나씩 처리하면서, 각각을 **분류 역할**(범주 역할과 상태 역할)의 작은 상태 기계를 따라 옮깁니다. 그리고 에이전트가 작업할 수 있는 브리프, 제보자에게 던지는 구체적인 질문, 또는 이유가 기록된 채 닫힌 이슈 중 하나를 남깁니다.

**당신이 만들지 않은** 이슈만을 위한 것입니다. 날것의 버그 제보, 들어온 기능 요청, 예고 없이 도착한 외부 풀 리퀘스트처럼 바깥에서 제보자가 남긴 모양 그대로 트래커에 떨어진 일 말입니다. [to-tickets](https://aihero.dev/skills-to-tickets) 가 만든 [티켓](https://www.aihero.dev/ai-coding-dictionary/ticket)은 구조상 이미 에이전트가 작업할 준비가 돼 있고, 그 위에 `triage` 를 돌리는 것은 잘해야 헛수고입니다. 규칙은 단순합니다. `/triage` 는 들어온 이슈만을 위한 것이지 당신이 직접 만든 이슈를 위한 것이 아닙니다.

손으로 라벨 붙이는 것과 구분되는 두 번째 지점은 추천하고 기다린다는 것입니다. 범주와 상태 판단을 근거와 함께 말해주고, 코드베이스에서 발견한 것도 알려주고, 당신이 지시하기 전까지 아무것도 적용하지 않습니다.

## 언제 꺼내 쓰나

`/triage` 라고 친 다음 원하는 것을 평범한 말로 설명해서 부릅니다. [에이전트](https://www.aihero.dev/ai-coding-dictionary/agent)가 알아서 꺼내 쓰지 않습니다. "내가 봐야 할 것들 보여줘", "#42 좀 보자", "#42 를 ready-for-agent 로 옮겨줘" 같은 식입니다.

| 당신이 가진 것 | 어디로 갈 것인가 |
| --- | --- |
| 남들이 보낸 날것 제보로 가득한 트래커 | `/triage` |
| 아직 아무 데도 안 적은 당신의 거친 아이디어 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| [스펙](https://www.aihero.dev/ai-coding-dictionary/spec)으로 바꿀 정리된 대화 | [to-spec](https://aihero.dev/skills-to-spec) |
| 에이전트용 티켓으로 쪼갤 스펙 | [to-tickets](https://aihero.dev/skills-to-tickets) |
| 라벨이 아니라 근본 원인이 필요한 확인된 버그 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

## 사전 조건

`triage` 는 이슈 트래커를 읽고 쓰므로, [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 가 먼저 그 트래커와 라벨 어휘를 설정해 뒀어야 합니다. 아래의 역할 이름은 **표준**입니다. 당신 트래커의 라벨 문자열은 다를 수 있고, 그 대응표를 설정이 제공합니다. 트래커가 이미 표준 이름을 정확히 쓰고 있다면 대응할 것도 설정할 것도 없습니다.

트래커 설정은 외부 풀 리퀘스트를 요청 창구로 칠지, 누구를 외부로 칠지도 정합니다. 그 플래그는 기본이 꺼짐이고 더 이상 설정 단계의 질문이 아니므로, PR 을 범위에 넣고 싶으면 `docs/agents/issue-tracker.md` 에서 켜십시오.

## 상태 기계

분류된 모든 항목은 정확히 하나의 범주 역할과 하나의 상태 역할을 달고 끝납니다. 범주는 둘입니다. `bug`(뭔가 고장남)와 `enhancement`(새 기능 또는 개선). 상태는 다섯입니다.

| 상태 | 뜻 |
| --- | --- |
| `needs-triage` | 당신이 평가해야 합니다. 라벨 없는 이슈가 보통 처음 떨어지는 자리입니다. |
| `needs-info` | 제보자를 기다리는 중. 답이 오면 `needs-triage` 로 돌아옵니다. |
| `ready-for-agent` | 완전히 서술됐고 에이전트 브리프가 붙어 있습니다. [자리 비운](https://www.aihero.dev/ai-coding-dictionary/afk) 에이전트가 가져갈 수 있습니다. |
| `ready-for-human` | 같은 브리프에, 왜 이것이 위임될 수 없는지가 더해집니다. 판단, 외부 접근 권한, 수동 테스트 같은 이유입니다. |
| `wontfix` | 이유가 기록된 채 닫힘. |

어휘는 그게 전부이고, "상태 역할은 정확히 하나" 라는 불변 조건이 질의를 단순하게 유지합니다. 동시에 이 [스킬](https://www.aihero.dev/ai-coding-dictionary/skill)에서 가장 많은 요청이 몰리는 영역이기도 합니다. 서술은 끝났지만 다른 이슈에 막힌 일을 위한 여섯 번째 상태, 미래의 계기에 걸린 `deferred` 작업, 그리고 종착점인 `implemented` 상태를 요청받았습니다. 어느 것도 출시되지 않았습니다. 아래 질문들을 보십시오.

`wontfix` 는 세 갈래로 나뉘고, 그중 하나만 지식 기반에 기록하기 때문에 차이가 중요합니다.

| 왜 닫는가 | 무슨 일이 일어나나 |
| --- | --- |
| 이미 구현됨 | 이미 어디에 있는지 가리키는 댓글. `.out-of-scope/` 에는 아무것도 쓰지 않습니다. 거부된 기능이 아니라 만들어진 기능이고, 거기 넣으면 중복 확인을 오염시키기 때문입니다. |
| 거부된 버그 | 정중한 설명 후 닫기. |
| 거부된 기능 요청 | `.out-of-scope/` 에 파일 하나, 닫는 댓글에서 링크, 그리고 닫기. |

`.out-of-scope/` 는 이슈마다가 아니라 거부된 **개념**마다 마크다운 파일 하나이고, 데이터베이스 행이 아니라 짧은 설계 문서로 쓰입니다. 무엇이 거부됐는지, 왜인지, 그리고 그것을 요청한 모든 이슈를 담습니다. `triage` 는 무언가를 평가하기 전에 그 디렉터리 전체를 읽고, 키워드가 아니라 개념으로 대조합니다. 그래서 "야간 테마" 가 `dark-mode.md` 와 맞습니다. 일치하는 것을 만나면 요청을 처음부터 다시 논쟁하는 대신 옛 결정을 꺼내 보여주고 지금도 같은 생각인지 묻습니다.

## 브리프 전에 확인

[캐묻기](https://www.aihero.dev/ai-coding-dictionary/grilling) 전에 `triage` 는 그 주장이 실제로 성립하는지 확인합니다. 버그라면 제보자의 절차대로 재현합니다. PR 이라면 브랜치를 받아 해당 테스트를 돌립니다. 그다음 셋 중 무엇이 일어났는지 보고합니다. 코드 경로와 함께 확인됨, 재현 실패, 또는 시도할 만큼의 정보가 없음. 마지막 것은 그 자체로 가장 강한 `needs-info` 신호입니다.

같은 과정에서 코드베이스를 상대로 검사 둘을 더 돌립니다. **중복**(이미 구현돼 있나? 제보자의 표현이 아니라 도메인 개념으로 검색합니다)과 **과거 거부**(`.out-of-scope/` 가 이미 아니라고 말하고 있나?)입니다. 둘 다 싸고, 둘 다 걸리면 `wontfix` 를 냅니다.

이 모든 것이 산출물 하나를 좋게 만들려고 있습니다. **에이전트 브리프**, 즉 이슈가 `ready-for-agent` 로 옮겨갈 때 게시되는 구조화된 댓글입니다. 일단 게시되면 브리프가 계약이고 원래 제보는 맥락일 뿐입니다. 브리프는 정밀하기보다 **오래가도록** 쓰입니다. 이슈가 `ready-for-agent` 에 몇 주씩 앉아 있는 동안 그 아래 코드가 움직이기 때문입니다. 그래서 타입과 시그니처와 동작 계약을 이름으로 대고, 파일 경로나 줄 번호는 절대 쓰지 않습니다. 확인된 재현은 추측보다 훨씬 강한 브리프를 만듭니다.

## PR 은 코드가 붙은 이슈다

트래커가 외부 풀 리퀘스트를 요청 창구로 취급하는 경우, PR 도 같은 기계를 통과합니다. 같은 범주, 같은 상태, 같은 전이입니다. 상태가 차이(diff)를 상대로 읽힐 뿐입니다. `ready-for-agent` 는 브리프가 붙어 있고 에이전트가 코드에 대해 다음 단계를 밟아야 한다는 뜻이고, `ready-for-human` 은 사람이 병합할 준비가 됐다는 뜻입니다. PR 에 붙는 브리프는 무에서 그것을 어떻게 만드는지가 아니라 지금 있는 차이에 무엇이 더 필요한지를 서술합니다.

발견 과정은 *외부* PR 만 띄웁니다. 동료가 작업 중인 브랜치는 분류 대상이 아니기 때문입니다. 그 거름망은 발견 단계에만 적용되고, PR 을 명시적으로 이름 대면 누가 썼든 분류됩니다. 거친 부분 하나가 있습니다. GitHub 템플릿의 외부 PR 목록 명령어가 `gh pr list` 에 `gh` 가 제공하지 않는 `authorAssociation` 필드를 요구해서, 적힌 그대로의 명령어는 그냥 실패합니다 ([#468](https://github.com/mattpocock/skills/issues/468)).

## 자주 나오는 질문

**`/to-spec` 과 `/to-tickets` 를 돌렸는데 그 티켓들이 분류 안 된 채 있습니다. 그 위에 `/triage` 를 돌리나요?**
아닙니다. 이미 에이전트가 작업할 준비가 돼 있습니다. `to-tickets` 가 발행하면서 `ready-for-agent` 라벨을 붙이는데, 바로 자리 비운 실행기가 한 단계 더 거치지 않고 집어 들게 하려는 것입니다. 이 문제를 겪은 사용자는 스펙 흐름을 돌리고 결과물에 `needs-triage` 가 붙은 것을 보았고, 자리 비운 실행기가 전부 무시하는 것을 발견했습니다. `triage` 는 바깥에서 들어온 일을 위한 진입로이고, 스펙 흐름은 당신이 시작한 일을 위한 차선입니다. 둘은 `ready-for-agent` 에서 만나지 그 전에 만나지 않습니다.

**`to-spec` → `to-tickets` → `implement` 흐름이 생긴 지금도 `triage` 가 유효한가요?**
들어오는 일이 있을 때만요. `triage` 는 그 척추보다 먼저 있었고 다른 일을 합니다. 남들이 등록한 제보를 위한 차선이죠. 트래커의 모든 것이 당신 자신의 계획에서 나왔다면 이걸 열 일이 거의 없을 겁니다. 공개된 무언가를 유지보수하거나 팀이 당신에게 버그를 등록한다면, 이것이 정문입니다. 주된 용도는 외부 기여자로부터 이슈를 받는 오픈소스 레포입니다.

**에이전트가 `ready-for-agent` 를 붙이려 했는데 `gh` 가 그런 라벨이 없다고 합니다.**
알려진 열린 버그입니다 ([#616](https://github.com/mattpocock/skills/issues/616)). `setup-matt-pocock-skills` 는 라벨 어휘를 `docs/agents/triage-labels.md` 에 쓰지만 트래커에 라벨을 만들지는 않습니다. 상태 라벨 다섯과 범주 라벨 둘을 `gh label create` 나 트래커 UI 로 한 번 직접 만들면 멈춥니다. 이슈에 링크된 커뮤니티 수정 브랜치가 있지만 병합되지 않았습니다.

**상태 다섯 개로는 부족합니다. blocked 나 deferred 나 implemented 는요?**
이 스킬에 가장 많이 등록된 구멍이고, 세 가지 모양으로 옵니다. 완전히 서술됐지만 다른 이슈가 닫히기를 기다리는 이슈 ([#139](https://github.com/mattpocock/skills/issues/139)). 제보자의 불만은 거기서 `ready-for-agent` 가 "엄밀히는 참" 이지만 오해를 부르고, 그래서 에이전트가 집어 들었다가 벽에 부딪힌다는 것이었습니다. 의도는 있지만 아직 실행 가능하지 않은, 계기에 걸린 미래 작업 ([#297](https://github.com/mattpocock/skills/issues/297)). 그리고 "구현됨, 검증 대기" 를 위한 종착 상태인데, 이것이 없으면 자리 비운 실행기가 끝난 티켓을 다시 대기열에 넣을 수 있습니다. 막힘 사례가 실재한다는 데는 동의가 있었지만 이름(`blocked` 냐 `paused` 냐)은 미정입니다. 어느 것도 출시되지 않았습니다. 사람들이 쓰는 우회책은 범주 옆에 레포 전용 라벨을 하나 더 두는 것인데, 표준 상태 자리를 정직한 것으로 채워두는 대신 스킬이 그것을 모른다는 비용을 치릅니다. 어떤 커뮤니티 파생본은 더 나아가 `needs-slicing`, `tracking`, 그리고 작업량 라벨을 추가합니다. 동작하지만 그건 그쪽 것이지 이 스킬의 것이 아닙니다.

**`/diagnosing-bugs` 와 어떻게 다른가요?**
여기의 확인 단계는 의도적으로 얕습니다("이게 진짜인가, 대략 어디에 사는가" 에 답할 정도). 근본 원인을 찾으려는 것이 아닙니다. 제보자의 절차로 몇 분 안에 버그가 재현되지 않으면 정직한 수는 `needs-info` 이거나, 지금 쫓고 싶다면 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) 입니다. 현재 두 스킬의 글 중 어느 쪽도 상대를 언급하지 않습니다. 어떤 사용자가 그 이음매를 발견했고 아직 열려 있습니다.

**백로그 전체를 가리키고 돌게 놔둬도 되나요?**
요청할 수는 있지만 무엇을 읽는지 지켜보십시오. "봐야 할 것 보여줘" 과정은 *선택*을 위한 값싼 목록 조회입니다. 당신이 하나를 고르면 그다음에 고른 것에 대해 온전한 [컨텍스트](https://www.aihero.dev/ai-coding-dictionary/context)를 모읍니다. 스무 개를 한꺼번에 돌리면 에이전트가 조용히 그 값싼 목록을 근거로 삼을 수 있는데, 거기에는 이슈 본문은 있어도 댓글이 없습니다. 어떤 사용자가 정확히 여기에 걸렸습니다. 이슈 셋에 이미 "이미 고쳐졌으니 닫기를 권함" 이라는 댓글이 달려 있었는데, 셋 다 새 에이전트 브리프를 받았습니다. 일괄 처리를 원한다면 이슈마다 댓글을 반드시 읽으라고 명시하십시오.

**Linear 나 GitHub Issues 가 아닌 것에서도 되나요?**
됩니다. 트래커는 설정이지 못 박힌 가정이 아니고, 사람들은 Linear(`linear` CLI 를 통해), GitLab, `.scratch/` 아래 평범한 마크다운 파일을 상대로 돌립니다. 흔한 조합은 이슈와 계획은 Linear, 코드와 PR 은 GitHub 로 나누는 것입니다. "이슈 트래커" 라고 말하는 스킬은 Linear 로, "PR" 이라고 말하는 스킬은 GitHub 로 대응됩니다. 로컬 마크다운 트래커에는 생성된 파일이 인수 조건을 두 번 담을 수 있는 열린 템플릿 버그가 있습니다. 최상위에 한 번, 에이전트 브리프 안에 한 번입니다 ([#200](https://github.com/mattpocock/skills/issues/200)).

## 제대로 동작하고 있다는 신호

- 건드린 모든 항목이 정확히 범주 역할 하나와 상태 역할 하나로 끝납니다. 0개도, 충돌하는 상태 2개도 아닙니다.
- 라벨을 바꾸고 넘어가는 대신, 근거가 달린 추천을 주고 멈춥니다.
- 무언가가 `ready-for-agent` 에 닿기 전에 버그가 재현됐거나 PR 을 받아 돌려봤습니다.
- 쓰는 브리프가 타입과 동작을 이름으로 대고, 파일 경로와 줄 번호를 담지 않습니다.
- 여섯 달 전에 거부된 요청이 다시 오면, 새로 분류하는 대신 그렇다고 말하며 옛 이유를 인용합니다.
- 게시하는 모든 댓글이 `> *This was generated by AI during triage.*` 로 시작합니다.

## 전체에서 어디에 있나

`triage` 는 주 사슬의 단계가 아니라 **진입로**입니다. 주 흐름은 당신이 떠올린 아이디어에서 시작하고(캐묻기, 스펙, 티켓, 구현, 리뷰), `triage` 는 대신 도착한 일을 위한 나란한 차선입니다. 합류 지점은 같습니다. 브리프가 붙고 `ready-for-agent` 라벨이 달린 이슈이고, [implement](https://aihero.dev/skills-implement) 가 [to-tickets](https://aihero.dev/skills-to-tickets) 의 티켓과 똑같이 집어 듭니다. 브리프를 쓰기 전에 요청을 날카롭게 다듬어야 할 때, `triage` 는 [grilling](https://aihero.dev/skills-grilling) 과 [domain-modeling](https://aihero.dev/skills-domain-modeling) 을 함께 돌립니다. 한 번에 질문 한 묶음씩이라, 결정이 내려지는 대로 `CONTEXT.md` 와 ADR 에 떨어집니다. 어느 차선에 있는지 모르겠으면 [ask-matt](https://aihero.dev/skills-ask-matt) 이 안내합니다.
